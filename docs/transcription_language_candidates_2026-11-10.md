# 候補言語が複数あるときの文字起こし (2026-11-10)

対象: ローカル Whisper と OpenAI 互換 API (Groq / OpenAI / カスタムサーバー)。
Google と Deepgram は変更なし。

候補言語が複数になるのは主にスピーカー側 (翻訳先の言語が候補になるので、翻訳先を
2〜3 個有効にしているとき)。

## 1. 問題

`AudioTranscriber._finalizeAndTranscribe` は候補言語ごとに
`provider.transcribe(force_language=False)` を呼び、検出された言語が候補と一致したら
打ち切っていた。言語を指定しない呼び出しは、どの候補に対して呼んでも同じ結果を返す
(temperature 0 なので決定的)。このため次の 2 つが起きていた。

1. **同じ音声を何度もデコードする。** 検出された言語が k 番目の候補なら k 回、候補に
   無い言語 (自分と同じ言語で話す人など) なら候補の数だけデコードしていた。
   API エンジンでは、その回数だけ同じ音声を送って課金されていた。
2. **結果の言語が常に最初の候補になる。** どの呼び出しも同じ confidence を返すので、
   「confidence がより高い結果を採用する」比較では最初の候補の結果が残り続ける。
   韓国語の発話を正しく韓国語で書き起こしても、言語は最初の候補 (例: English) として
   翻訳に渡り、英語→日本語として訳されていた。

OpenAI 互換 API には、もう 1 つ原因があった。verbose_json の `language` を言語コード
(`"ja"`) としか比べていなかったが、OpenAI 公式は言語名 (`"japanese"`) を返す。
一度も一致しないので、常に候補の数だけ呼び直していた。

## 2. 変更

- `LocalWhisperProvider.transcribe_candidates` / `OpenAICompatibleTranscriptionProvider.transcribe_candidates`
  を追加。1 回だけ文字起こしし、検出された言語に一致する候補 (無ければ従来どおり
  最初の候補) の添字を返す。
- `AudioTranscriber` は、候補が複数あり、プロバイダがこのメソッドを持つときはそれを
  1 回だけ呼ぶ。失敗しても候補ごとに呼び直さない (同じ呼び出しなので結果は変わらない)。
- API が返す言語は、コード・言語名 (大文字小文字を区別しない)・Whisper 独自の名前
  (`chinese` → `zh`、`tagalog` → `tl` など) のどれでも候補と照合する。
- 候補が 1 つのとき (言語を指定して文字起こしする) は変更なし。

## 3. 実測

faster-whisper `base`、CPU int8 4 スレッド、beam 5 (アプリと同じ呼び出し)。
音声は FLEURS (google/fleurs) の validation から ja / en / ko / zh を各 12 発話、
先頭の無音を除いた最初の 4 秒。合計 48 クリップ。

| 候補 (この順) | | デコード回数 | 所要時間 | 言語が正しい (候補にある言語のクリップ) | 書き起こし |
|---|---|---|---|---|---|
| en, ko, zh | 変更前 | 106 | 137.0 秒 | 12/36 | — |
| | 変更後 | 48 | 60.6 秒 | 34/36 | 変更前と同一 48/48 |
| ja, en | 変更前 | 86 | 106.3 秒 | 12/24 | — |
| | 変更後 | 48 | 58.9 秒 | 23/24 | 変更前と同一 48/48 |

- 変更前に言語が正しかったのは、最初の候補の言語のクリップだけ (12/36、12/24)。
- 変更後に残る誤りは、Whisper 自体が言語を取り違えたクリップ (3 件)。
- 書き起こしの文字列は全クリップで変更前と同じ。変わるのは回数と言語だけ。

## 4. 検討したが入れなかったもの: 検出を候補の言語に絞る

Whisper は約 100 言語の中から言語を検出する。短い発話では候補に無い言語に倒れる
ことがあるので、「検出された言語が候補に無ければ、候補の中で最も確率の高い言語を
指定してデコードし直す」方法を評価した (`info.all_language_probs` を使う)。

方法: FLEURS の ja / en / ko / zh 各 60 発話の先頭 1.5 / 3 / 6 秒で言語の確率を取り、
候補の組ごとに集計。

制限なしの検出の正解数 (/60):

| 長さ | ja | en | ko | zh |
|---|---|---|---|---|
| 1.5 秒 | 11 (en と誤検出 45) | 59 | 43 (en と誤検出 13) | 57 |
| 3 秒 | 45 | 60 | 55 | 60 |
| 6 秒 | 60 | 60 | 60 | 60 |

短い発話の誤検出の大半は**英語**で、英語はたいてい候補に入っている。候補に絞っても
これは直らない。

絞った場合の内訳 (しきい値 = 候補の確率がこれ以上ならデコードし直す)。
改善 = 候補にある言語の発話が正しい言語になった数、取り違え = 候補の中の別の言語に
なった数、悪化 = 候補に無い言語の発話を候補の言語で書き起こすようになった数
(変更前は聞こえたままの言語で書き起こされる)。

| 候補 | しきい値 | 1.5 秒: 改善 / 取り違え / 悪化 | 3 秒: 改善 / 取り違え / 悪化 |
|---|---|---|---|
| ja, en | 0.05 | 2 / 3 / 17 | 1 / 6 / 9 |
| ja, en | 0.2 | 1 / 1 / 2 | 1 / 5 / 0 |
| en, ko, zh | 0.05 | 1 / 4 / 7 | 2 / 1 / 16 |
| en, ko, zh | 0.2 | 0 / 0 / 1 | 1 / 0 / 6 |
| ja, en, ko | 0.05 | 2 / 6 / 3 | 1 / 8 / 0 |
| ja, ko, zh (英語なし) | 0.02 | 42 / 23 / 7 | 9 / 6 / 2 |
| ja, ko, zh (英語なし) | 0.05 | 5 / 6 / 3 | 4 / 4 / 0 |

英語が候補にあると、改善は 120〜180 クリップあたり 1〜3 件で、取り違えと悪化が同じか
それ以上ある。英語が候補に無い組だけは低いしきい値で大きく改善する (42 件) が、
そのしきい値は他の組では悪化が大きい (en, zh の 3 秒で 40/120)。どのしきい値でも
全体として良くならないので入れなかった。

### 測っていないもの

- Whisper の他のサイズ (small 以上は短い発話の言語検出が良くなる見込み)。
- 実際の VRChat の音声。FLEURS は読み上げ音声。
- OpenAI 公式 / Groq の実 API (応答の形式は公開されている仕様に基づく)。
